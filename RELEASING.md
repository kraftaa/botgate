# Releasing Botgate

Botgate is public and currently publishes native binaries through GitHub
Releases, platform wheels through PyPI trusted publishing, and a manually
reviewed formula in `kraftaa/homebrew-tap`.

## Publishing model

- A version tag starts the `Release` workflow, which builds archives,
  installers, checksums, and a Homebrew formula as workflow artifacts. It has
  read-only repository permissions and does not create a GitHub release.
- The same tag starts the `PyPI` workflow. It verifies that the tag matches
  `Cargo.toml`, runs formatting, Clippy, and tests, builds the wheels, and then
  publishes through the protected `pypi` environment using short-lived OIDC
  credentials. There is no long-lived PyPI token.
- PyPI publishing is intentionally tag-only. Do not add an unqualified
  `workflow_dispatch` trigger that could publish an untagged branch.
- GitHub Actions are pinned to immutable commit SHAs. Preserve those pins when
  regenerating or editing workflows.

## Release checklist

1. Confirm the intended commit is on `main`, its CI run is green, and the
   working tree is clean.
2. Update the version in `Cargo.toml`, update `Cargo.lock`, and confirm the tag
   does not already exist.
3. Run the local release checks:

   ```sh
   cargo fmt --check
   cargo fmt --check --manifest-path fuzz/Cargo.toml
   cargo clippy --all-targets --locked -- -D warnings
   cargo test --locked
   cargo deny check advisories bans licenses sources
   ```

4. Commit and push the version bump. Wait for the `CI` workflow on `main` to
   succeed.
5. Create and push an annotated tag matching the package version, for example:

   ```sh
   git tag -a v0.4.2 -m "Botgate v0.4.2"
   git push origin v0.4.2
   ```

6. Confirm both tag workflows succeed. The PyPI workflow must complete its
   verification job before it can build or publish wheels.
7. Download the release workflow artifacts. Validate `sha256.sum`, run the
   binary on at least one supported platform, and test the generated installer.
8. Create the GitHub release from the audited artifacts and write release notes
   that summarize user-visible changes rather than only linking a commit diff.
9. Run `brew style --fix` and `brew test` on the generated `botgate.rb`. Remove
   a redundant explicit `version` if present, retain its `test do` block, and
   commit the audited formula to `kraftaa/homebrew-tap`.
10. Verify installation from PyPI and Homebrew in clean environments.

## One-time service configuration

PyPI trusted publishing uses:

- project: `botgate`
- owner: `kraftaa`
- repository: `botgate`
- workflow: `pypi.yml`
- environment: `pypi`

The `pypi` GitHub environment and corresponding PyPI trusted publisher must
remain configured. The repository-wide Actions token stays read-only; only the
PyPI publish job receives `id-token: write`.

The release workflow is generated by cargo-dist but intentionally omits its
publishing/host job. Regenerating it requires restoring the read-only workflow,
the immutable action pins, and the manual artifact-review process.
